# TIL - OpenAI Vision 기반 영수증 OCR Agent 구현

## 1. 작업 내용

영수증 OCR 기능을 위해 FastAPI Agent 서버에서 OpenAI Vision 기반 분석 API를 구현하고 테스트했다.  
이 단계에서는 백엔드가 업로드한 영수증 이미지를 AI가 분석해 OCR 원문과 식재료 후보를 반환하는 흐름을 다뤘다.

핵심 작업은 다음과 같다.

- FastAPI Agent OCR 분석 API 구현
- base64 이미지 요청 처리
- OpenAI Vision API 호출 구조 구성
- OCR 원문과 식재료 후보 반환
- Postman 기반 테스트
- base64, ImportError, Flyway checksum 문제 해결

---

## 2. Agent OCR 분석 API

Agent 서버에는 영수증 이미지를 분석하는 API를 추가했다.

| 기능 | Method | URL |
|---|---|---|
| 영수증 OCR 분석 | `POST` | `/agent/v1/receipts/analyze` |

요청은 이미지 파일 자체가 아니라 base64 문자열을 받는다.

```json
{
  "receiptAnalysisId": 1,
  "imageBase64": "base64 문자열",
  "mimeType": "image/jpeg"
}
```

Agent 서버의 역할은 다음과 같다.

```text
base64 이미지 수신
-> base64 유효성 검증
-> OpenAI Vision API 호출
-> 영수증 원문 텍스트 추출
-> 식재료 후보 추출
-> Backend가 처리할 수 있는 JSON 응답 반환
```

응답 형태는 다음과 같다.

```json
{
  "rawText": "영수증에서 읽은 전체 텍스트",
  "items": [
    {
      "name": "콩나물",
      "quantity": "1개"
    }
  ]
}
```

## 3. Backend와 Agent 역할 분리

이번 구조에서는 Spring Boot Backend와 FastAPI Agent의 역할을 분리했다.

| 구분 | 역할 |
|---|---|
| Spring Boot Backend | 인증, DB 저장, S3 업로드, 사전 재료 매칭, 냉장고 등록 정책 |
| FastAPI Agent | OpenAI Vision 호출, OCR 분석, 식재료 후보 추출 |

AI가 직접 DB를 수정하지 않도록 한 것이 중요하다.  
Agent는 후보만 반환하고, Backend가 서비스 정책에 맞게 저장하고 검증하는 구조가 더 안전하다.

---

## 4. OCR 결과 저장에 대한 판단

OCR 결과는 단순히 화면에 보여주고 끝내지 않고 DB에 저장하는 방향으로 잡았다.

이유는 문제가 생겼을 때 추적이 필요하기 때문이다.

확인해야 할 수 있는 지점은 다음과 같다.

- 이미지 업로드가 정상적으로 되었는지
- OpenAI Vision이 원문을 제대로 읽었는지
- 상품명 정제 과정에서 빠졌는지
- 사전 재료 매칭에서 실패했는지
- 사용자가 후보를 제외했는지

따라서 `rawText`와 후보 항목은 이후 Backend에서 저장하고, 사용자 승인 흐름으로 이어지게 할 예정이다.

---

## 5. 상품명 정제 기준

OpenAI Vision 프롬프트에는 브랜드명, 원산지, 용량, 가격, 행사 문구를 제거하도록 작성했다.  
하지만 테스트 결과 일부 후보에는 불필요한 단어가 남았다.

| OCR 후보 | 기대하는 재료명 |
|---|---|
| 국산 팽이버섯 | 팽이버섯 |
| 찹쌀이 콩나물 | 콩나물 |
| 강릉최가두부 | 두부 |

Agent에서 모든 상품명을 완벽하게 정제하려고 하기보다, Backend에서 `products` 사전 재료 테이블 기준으로 한 번 더 매칭하는 방식이 더 안정적이라고 판단했다.

즉, Agent는 후보 추출에 집중하고 Backend는 서비스에서 사용할 재료인지 판단하는 역할을 맡는다.

## 6. base64 테스트 트러블슈팅

Postman에서 Agent OCR API를 테스트할 때 base64 관련 문제가 있었다.

처음에는 `imageBase64`에 실제 base64 문자열이 아니라 임시 문구를 넣어 `400` 오류가 발생했다.  
이후 이미지 파일을 base64로 변환해 넣었지만, 줄바꿈이 포함되어 `422 JSON decode error`가 발생했다.

해결 명령어는 다음과 같다.

```bash
base64 -i 이미지파일경로 | tr -d '\n' | pbcopy
```

`pbcopy`는 결과를 화면에 출력하지 않고 클립보드에 복사한다.  
처음에는 아무 출력이 없어서 실패한 줄 알았지만, 정상 동작이었다.

핵심은 JSON 문자열 안에 base64 줄바꿈이 들어가면 요청 Body가 깨질 수 있다는 점이다.

## 7. FastAPI ImportError 해결

Agent 서버 실행 중 `ImportError`도 발생했다.

원인은 API 파일에서 import하는 schema 클래스명과 실제 schema 파일에 정의된 클래스명이 달랐기 때문이다.

확인 순서는 다음과 같았다.

1. schema 파일에 정의된 요청/응답 클래스명 확인
2. API 파일의 import 이름 수정
3. `main.py`에서 router 등록 여부 확인
4. Agent 서버 재실행

FastAPI는 서버 시작 시 router와 schema import를 모두 확인하므로, 클래스명 하나만 맞지 않아도 서버가 실행되지 않는다.

## 8. Flyway checksum 불일치

Backend에서는 dev 브랜치 병합 후 Flyway checksum 불일치로 실행이 실패했다.

Flyway는 이미 DB에 적용된 migration 파일이 이후 변경되었는지 checksum으로 확인한다.  
이미 적용된 파일의 내용, 공백, 줄바꿈이 바뀌면 같은 버전인데 내용이 달라졌다고 판단해 실행을 막는다.

정리한 원칙은 다음과 같다.

- 이미 적용된 migration 파일은 수정하지 않는다.
- 변경이 필요하면 새 버전 migration 파일을 만든다.
- 공백이나 줄바꿈 변경도 checksum 변경 원인이 될 수 있다.
- 팀 프로젝트에서는 migration 버전 충돌을 특히 조심해야 한다.

## 9. 테스트 결과와 남은 작업

Postman으로 영수증 이미지 업로드와 Agent OCR 분석을 확인했다.

확인한 내용은 다음과 같다.

- 이미지 업로드 성공
- S3 임시 저장 성공
- `receiptAnalysisId` 응답 확인
- 상태값 `PENDING` 반환 확인
- Agent OCR 분석 `200 OK` 확인
- `rawText`와 식재료 후보 반환 확인

추출 후보 예시는 다음과 같았다.

| 추출 후보 |
|---|
| 찹쌀이 콩나물 |
| 국산 팽이버섯 |
| 국산 느타리버섯 |
| 국산 만가닥버섯 |
| 국산 꽈리고추 |

아직 남은 작업은 Backend와 Agent를 실제로 연결하고, Agent 응답을 `receipt_analysis`와 `receipt_analysis_items`에 저장하는 것이다.  
이후 후보 상품명을 사전 재료와 매칭하고, 사용자가 승인한 후보를 냉장고에 일괄 등록하는 흐름까지 확장할 예정이다.
