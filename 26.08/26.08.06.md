# TIL - 냉파마스터 2차 리팩토링 및 AI 추천 기능 확장

## 1. 학습 주제

냉파마스터 2차 프로젝트에서는 기존 장보기 기능을 확장해, 사용자의 냉장고 상태와 장보기 목록을 기반으로 AI가 필요한 재료를 추천하는 기능을 구현했다.

핵심 작업은 다음과 같다.

- AI 장보기 추천 MVP 구현
- AI 대화 세션 및 메시지 기록 저장
- LLM 사용량 로그 저장
- 프론트 AI 추천 화면 연동
- 관리자 LLM 사용량 조회 API 및 화면 구현
- Flyway migration 문제 해결

---

## 2. AI 장보기 추천 흐름

기존 장보기 기능은 사용자가 직접 재료를 검색하고 추가하는 방식이었다.  
사용자의 현재 상태를 기반으로 추천 후보를 만들고, AI Agent가 장보기 재료를 추천하는 흐름을 추가했다.

전체 흐름은 다음과 같다.

```text
프론트에서 AI 추천 요청
-> Backend가 사용자 상태 조회
-> 냉장고/장보기/못 먹는 재료 기준으로 제외 목록 생성
-> 추천 후보를 FastAPI Agent 서버에 전달
-> Agent가 추천 결과 생성
-> Backend가 결과 반환
-> 사용자가 선택한 항목만 장보기 목록에 추가
```

중요한 점은 AI 추천 결과를 바로 DB에 저장하지 않았다는 것이다.  
AI는 제안만 하고, 실제 장보기 목록 반영은 사용자가 직접 선택하도록 했다.

---

## 3. 추천 제외 기준

추천 결과가 사용자 상황과 맞도록 다음 재료는 제외했다.

- 이미 냉장고에 있는 재료
- 아직 구매하지 않은 장보기 항목
- 사용자가 못 먹는 재료
- 현재 추천 화면에 이미 노출된 재료

특히 재추천 시 같은 항목이 반복되는 문제가 있어, 프론트에서 현재 추천된 `productId`를 `excludeProductIds`로 전달하도록 보완했다.

```text
기존 제외 목록 + 화면에 이미 노출된 추천 항목
= 최종 추천 제외 목록
```

## 4. AI 대화 기록과 사용량 로그

AI 추천은 단발성 응답으로 끝내지 않고 사용자별 기록으로 저장했다.

저장 구조는 다음과 같다.

| 테이블 | 역할 |
|---|---|
| `conversation_sessions` | AI 추천 요청 단위 세션 |
| `conversation_messages` | 세션 안의 사용자 요청과 AI 응답 |
| `llm_usage_logs` | 모델명, 토큰 수, 예상 비용, 성공/실패 상태 기록 |

LLM 사용량 로그에는 `promptTokens`, `completionTokens`, `totalTokens`, `estimatedCost`, `status`, `failureMessage` 등을 저장했다.

실제 LLM이 아닌 rule-based fallback이 동작한 경우에는 `modelName`을 `rule-based-mvp`로 저장하고 토큰과 비용은 0으로 처리했다.

## 5. 프론트 및 관리자 기능

프론트 장보기 화면에는 AI 추천 버튼과 추천 결과 카드를 추가했다.

사용자 흐름은 다음과 같다.

```text
AI 추천 버튼 클릭
-> 추천 카드 표시
-> 사용자가 담기 선택
-> 선택한 항목만 장보기 목록에 추가
-> 추가된 항목은 추천 목록에서 제거
```

관리자 화면에서는 전체 LLM 사용량 로그를 조회할 수 있도록 했다.

관리자가 확인할 수 있는 정보는 다음과 같다.

- 사용자 이메일과 닉네임
- 모델명
- Prompt / Completion / Total 토큰
- 예상 비용
- 성공/실패 상태
- 실패 메시지
- 호출 일시

예상 비용은 달러 기준 저장값을 원화로도 볼 수 있도록 환율 변환 표시를 추가했다.

## 6. Flyway Migration 트러블슈팅

AI 대화 기록과 LLM 사용량 로그 테이블을 추가하면서 Flyway migration이 적용되지 않는 문제가 있었다.

확인한 내용은 다음과 같다.

```sql
SELECT installed_rank, version, description, script, success
FROM flyway_schema_history
ORDER BY installed_rank;
```

```sql
SELECT current_database();
SELECT current_schema();
```

```sql
SELECT table_name
FROM information_schema.tables
WHERE table_schema = 'public'
  AND table_name IN (
    'conversation_sessions',
    'conversation_messages',
    'llm_usage_logs'
  );
```

원인은 migration 파일 자체보다 Backend가 바라보는 DB와 직접 확인하던 DB가 다를 가능성이었다.  
`application-secret.env`의 DB 접속 정보와 실제 실행 로그의 DB URL을 확인한 뒤, Backend를 재실행해 migration 반영 여부를 확인했다.

## 7. 핵심 정리

1. AI 추천은 자동 저장보다 사용자 승인 후 반영하는 구조가 안전하다.
2. 추천 기능에서는 냉장고, 장보기, 못 먹는 재료, 이미 노출된 추천 항목을 제외해야 한다.
3. AI 응답은 세션과 메시지로 저장하면 이후 조회와 분석이 가능하다.
4. LLM 기능은 토큰 수, 비용, 실패 로그를 함께 남겨야 운영 관점에서 관리할 수 있다.
5. 관리자 화면에서는 전체 AI 사용량을 확인할 수 있어야 한다.
6. Flyway 문제가 생기면 migration 파일뿐 아니라 실제 연결 DB, schema, `flyway_schema_history`, 테이블 존재 여부를 함께 확인해야 한다.
