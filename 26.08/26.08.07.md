# TIL - 냉파마스터 영수증 OCR Agent 기반 설계

## 1. 작업 내용

냉파마스터 2차 프로젝트에서 영수증 OCR 기능을 위한 기반 구조를 설계하고 구현했다.  
기존 냉장고 등록은 사용자가 재료를 하나씩 검색해서 직접 입력하는 방식이었지만, 이번 기능은 영수증 이미지를 기반으로 구매한 식재료 후보를 추출하고 이후 냉장고 등록까지 이어질 수 있도록 만드는 것이 목표다.

이번 단계에서는 AI 분석 자체보다, 분석 결과를 안전하게 저장하고 관리할 수 있는 Backend 기반을 먼저 잡았다.

- 영수증 분석 테이블 구조 설계
- OCR 결과 후보 항목 테이블 설계
- 영수증 이미지 업로드 API 구현
- 이미지 파일 검증 처리
- S3 임시 저장 흐름 구현
- 업로드 성공 시 분석 row를 `PENDING` 상태로 생성

## 2. 영수증 OCR 기능의 기본 방향

처음에는 영수증을 분석한 뒤 바로 냉장고에 등록하는 흐름도 생각할 수 있다.  
하지만 AI가 추출한 결과는 항상 정확하지 않고, 영수증에는 식재료 외에도 할인 문구, 봉투, 브랜드명, 원산지, 가격 등이 함께 포함된다.

그래서 AI 결과를 바로 사용자 냉장고 데이터로 반영하지 않고, 먼저 후보 데이터로 저장한 뒤 사용자가 승인한 항목만 등록하는 구조로 잡았다.

```text
영수증 이미지 업로드
-> OCR 분석
-> 식재료 후보 생성
-> 사용자 확인
-> 승인한 항목만 냉장고 등록
```

이 구조는 자동화보다 데이터 안전성을 우선한 방식이다.

---

## 3. 영수증 관련 테이블 설계

영수증 분석을 관리하기 위해 핵심 테이블을 나누었다.

| 테이블 | 역할 |
|---|---|
| `receipt_analysis` | 영수증 분석 1건의 상태와 OCR 원문 저장 |
| `receipt_analysis_items` | OCR 결과로 추출된 식재료 후보 항목 저장 |

`receipt_analysis`에는 업로드 사용자, 원본 파일명, S3 object key, 분석 상태, OCR 원문, 실패 메시지 등을 저장한다.

OCR 원문을 저장하는 이유는 디버깅 때문이다.  
예를 들어 사용자가 “영수증에 두부가 있는데 왜 후보에 안 나왔지?”라고 했을 때, AI가 실제로 어떤 텍스트를 읽었는지 확인할 수 있어야 한다.

---

## 4. 후보 상태 관리

OCR 결과 후보는 MVP 기준으로 단순하게 관리했다.

| 상태 | 의미 |
|---|---|
| `PENDING` | 아직 사용자가 처리하지 않은 후보 |
| `REGISTERED` | 냉장고에 등록된 후보 |
| `REJECTED` | 사용자가 제외한 후보 |

처음부터 상태를 너무 세분화하면 구현 복잡도가 커진다.  
이번 단계에서는 후보 조회, 제외, 승인 후 등록 흐름을 표현할 수 있는 최소 상태만 두었다.

## 5. 영수증 이미지 업로드 API

영수증 이미지는 JSON Body가 아니라 `multipart/form-data` 형식으로 받았다.

| 기능 | Method | URL |
|---|---|---|
| 영수증 이미지 업로드 | `POST` | `/api/v1/receipts/images` |

컨트롤러에서는 요청 형식을 명확히 제한했다.

```java
@PostMapping(value = "/images", consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
```

`consumes`는 해당 API가 어떤 요청 형식을 받을 수 있는지 지정하는 옵션이다.  
즉, 이 API는 JSON이 아니라 파일 업로드 요청을 받는 API라는 의미다.

## 6. 이미지 검증과 S3 임시 저장

이미지 업로드 시 다음 항목을 검증했다.

| 검증 항목 | 처리 |
|---|---|
| 파일 없음 | `400 Bad Request` |
| 빈 파일 | `400 Bad Request` |
| `jpg`, `jpeg`, `png` 외 확장자 | `400 Bad Request` |
| 10MB 초과 | `400 Bad Request` |
| S3 업로드 실패 | `500 Internal Server Error` |

이미지는 백엔드 서버 로컬 디스크에 저장하지 않고 S3에 임시 저장했다.

S3를 사용한 이유는 다음과 같다.

- 서버 로컬 저장소에 의존하지 않아도 된다.
- 배포 환경이 바뀌어도 파일 저장 위치를 유지할 수 있다.
- 이미지 파일과 애플리케이션 서버를 분리할 수 있다.
- 처리 완료 후 삭제하는 흐름을 만들기 쉽다.

업로드가 성공하면 `receipt_analysis` row를 생성하고 상태는 `PENDING`으로 저장한다.  
아직 OCR 분석이 끝난 것이 아니라, “이미지만 업로드된 상태”이기 때문이다.

---

## 7. 정리

이번 작업에서는 영수증 OCR 기능의 첫 기반을 만들었다.  
핵심은 AI 분석 결과를 바로 냉장고에 반영하지 않고, 분석 상태와 후보 데이터를 분리해 관리하는 구조를 잡은 것이다.

영수증 OCR은 자동화 기능처럼 보이지만, 실제 서비스 데이터에 영향을 주는 기능이므로 사용자의 최종 승인 흐름이 필요하다.  
다음 단계에서는 FastAPI Agent에서 OpenAI Vision으로 이미지를 분석하고, 식재료 후보를 추출하는 흐름을 연결할 예정이다.
